Meta History Book · Open cultural data

Artwork of the Day turns Wikidata into a daily, cited art-history experience.

A deterministic Flask application that selects artworks by artist birthday, enriches them from open knowledge graphs, and republishes the result as human-readable pages plus Linked Art and IIIF records.

The project's core bet is trust over generated fluency: the prose layer is assembled from Wikidata statements and attributed Wikipedia summaries, while the same dossier powers social previews, deep-zoom manifests, and dereferenceable cultural-heritage JSON-LD.

Why This Is Worthwhile

A reading surface for a graph that was not built to be read.

Wikidata is excellent at structured art facts, but it is not a finished interpretive experience. This repository bridges that gap without handing factual authority to a language model.

Thesis

The app treats open linked data as the source of record, then layers deterministic narration, notability-ranked traversal, and standards-based publication on top. It is less a gallery scraper than a small cultural-heritage data product.

What That Buys You

The architecture gives users explainable text, source attribution, shareable artwork pages, IIIF-compatible image viewing, and machine-readable records. Running cost stays low because there is no LLM, vector database, account system, or private API key in the runtime path.

Essence: cited, deterministic, standards-aware art history from open knowledge graphs.

Architecture At A Glance

A server-rendered API core with a vanilla browser shell.

The Flask app owns routing, rate limiting, caching, social previews, Linked Art, and IIIF. The browser shell progressively loads a daily gallery, base article, and deeper enrichment while retaining a no-build frontend posture.

Core Components

Small modules with clear cultural-data jobs.

The repo is organized around a Flask route layer, a SPARQL data layer, deterministic prose builders, and publication serializers. There are no background workers or queues in the current codebase.

Name Type / Role Responsibility
app.py Flask application Owns HTTP routes, in-process caches, rate limiting, share pages, JSON endpoints, Linked Art and IIIF delivery, and cache headers.
static/index.html Browser shell Loads the daily gallery, resolves explore clicks, fetches progressive article sections, manages theme persistence, and opens IIIF deep zoom.
sparql_library.py Graph query library Builds artwork/artist dossiers and discovers related entities, works, movements, collections, identifiers, and notability-ranked peers.
article_writer.py Base article builder Produces the immediate deterministic article sections from a known artwork and artist dossier.
enrichment.py Parallel orchestrator Fans out across SPARQL, Wikibase REST, and Wikipedia summary calls; drops failed optional layers without failing the whole article.
wikidata_facts.py Statement narrator Turns selected Wikidata properties into concise fact sentences through a curated template registry and safe fallback behavior.
wikibase_rest.py REST client Reads statement qualifiers, date spans, labels, and reference sources from the Wikibase REST API to reduce pressure on WDQS.
linked_art.py JSON-LD serializer Maps dossiers to object, visual, person, place, group, concept, and set records with authority equivalents where available.
iiif.py Manifest builder Uses Commons image metadata to emit IIIF Presentation 3.0 manifests suitable for deep-zoom viewers.
og_card.py Image renderer Generates branded 1200 x 630 JPEG preview cards for per-artwork social sharing routes.

Engineering Discipline

A pragmatic quality gate around deterministic data behavior.

CI installs pinned dependencies, runs Ruff linting and format checks, type-checks configured modules with mypy, import-smoke-tests the app, and runs pytest with coverage over the core Python modules.

Quality Machinery

The suite includes pure logic tests for narration and date formatting, mocked parser tests for SPARQL and Wikibase REST shapes, route tests through Flask's test client, and a specific degradation test showing one failed enrichment layer does not sink the whole article.

Human-In-The-Loop Boundary

Code review, deployment choice, and release validation remain human responsibilities. The project includes docs for deployment and Linked Art schema validation, but no branch-protection policy, production alerting, or runbook automation is visible in the repository.

Memory, State, Data

Mostly stateless, with bounded process memory.

There is no database in the repository. The system remembers only ephemeral runtime results, client preferences, generated cards, and cacheable external metadata; canonical data remains in Wikidata, Wikimedia Commons, and Wikipedia.

Honest Evaluation

Strong thesis, credible implementation, visible next hardening work.

The project is unusually grounded for a portfolio-scale data app. Its main risks are operational: shared Wikimedia dependency behavior, single-process state, externally hosted frontend assets, and limited production observability.

Strengths Worth Protecting

Strength Why It Matters
Deterministic content path Factual trust is a product feature: every article section is assembled from structured statements or attributed summaries, not free-form generation.
Right-sized API split SPARQL handles graph-shaped queries while Wikibase REST handles qualifiers and references, matching each API to its strengths.
Progressive enrichment Base content can render before slower layers finish, and tests confirm a failed enrichment query drops only that section.
Interoperability posture Linked Art JSON-LD, IIIF Presentation 3.0, HAL links, CORS, and authority equivalents make the output useful beyond the app UI.
Quality automation CI covers lint, formatting, type checking, import smoke tests, pytest, and coverage over the most important Python modules.

Risks & Gaps

Severity Gap Detail Status
HIGH Single-process cache and rate-limit defaults Memory-backed caches and rate limits are appropriate for one Waitress process, but multi-instance deployments need Redis or another shared backend. Open; documented in deploy notes
MED Observability is minimal Errors are largely printed, and the roadmap explicitly calls out structured logging and error tracking as future work. Open
MED Frontend depends on public CDNs The static page loads GA4, Bootswatch, FontAwesome, jQuery, Popper, Bootstrap, and OpenSeadragon from external URLs. That simplifies shipping but creates availability, privacy, and CSP/SRI hardening work. Partial
MED No browser-level E2E suite Route tests are strong, but there is no visible Playwright/Cypress coverage for date browsing, explore navigation, theme persistence, share UI, or deep zoom. Open
LOW Documentation drift WIKIDATA.md still mentions five Linked Art types in one section while the code and newer README/roadmap show seven. Open cleanup
LOW Live schema validation is manual validate_linked_art.py exists, but the main CI workflow does not run it, likely because it builds live sample records. Partial

Recommended Improvements

Concrete upgrades that fit the current architecture.

These are intentionally repo-specific: they extend the existing Flask, test, and open-data model rather than changing the product into a different system.

# Improvement Why / Payoff Effort
1 Add structured logging and request correlation Replace scattered print calls with JSON-friendly logs carrying route, QID, latency, cache hit/miss, and upstream failure type. S
2 Add Playwright smoke tests for the main user journeys Protect the browser workflows that route tests cannot see: daily load, explore click, date picker, gallery mode, share button, and deep zoom. M
3 Make shared cache/rate-limit storage a first-class deploy mode Add a tested Redis configuration path and deployment notes for multi-instance hosts, while keeping memory storage as local default. M
4 Harden frontend asset delivery Pin or vendor external assets, add SRI/CSP guidance, and remove unused legacy dependencies if Bootstrap JS/jQuery are not needed. M
5 Add citation footnotes for Wikibase references The REST layer already exposes reference sources; surfacing URLs and source labels would make the trust thesis even more inspectable. M

If only one thing: add structured observability around upstream calls and cache behavior. The system depends on external public APIs; knowing what failed, how often, and for which QIDs is the highest-leverage production improvement.

Usage Instructions

Run locally with Python; deploy as a WSGI container.

The app requires Python 3.10+ per project docs and runs on Python 3.12 in CI and the Docker image. Runtime dependencies are Flask, Flask-Limiter, Pillow, requests, and Waitress.

Local Setup

python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt -r requirements-dev.txt
python serve.py
pytest -q
ruff check .
ruff format --check .
mypy

Configuration

All environment variables are optional. Set AOTD_CONTACT in public deployments so Wikimedia requests include a responsible contact. Tune AOTD_RATELIMIT_DEFAULT, AOTD_RATELIMIT_STORAGE, AOTD_RATELIMIT_ENABLED, and AOTD_CACHE_MAX when traffic or topology changes. 

docker build -f Dockerfile.web -t aotd-web .
docker run --rm -p 5000:5000 -e AOTD_CONTACT=https://your/contact aotd-web
